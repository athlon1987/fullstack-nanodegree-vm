# Build specification — Malaysia Airports passenger platform (concept prototype)

This file is the contract between everyone who writes code in this folder. Read it fully before
writing anything, together with `docs/engineering/next16-notes.md` (framework rules for Next.js 16)
and `docs/design/design-system.md` (visual language and tokens). If the three disagree, this file
wins for architecture, the design-system file wins for look and feel, and the Next.js notes win for
framework mechanics.

## 1. What we are building

A unified digital platform for the airports operated by Malaysia Airports Holdings Berhad (MAHB):
one passenger experience across the network and a separate, coherent corporate section.

Proposition: **Malaysia Airports. Your journey, beautifully connected.**
Qualities: effortless, intelligent, reassuring, premium, distinctly Malaysian.

It is an independent concept prototype. It is **not** an official MAHB property and has no access
to MAHB operational systems. Three rules follow, and they are not negotiable:

1. **Never present simulated data as live.** Anything generated by the demo providers (flights,
   gates, wait times, availability, notices marked demo) is labelled "Demonstration data" wherever
   it appears, including search results, the concierge and notifications.
2. **Never invent facts.** Published content (fares, rates, hours, locations, procedures, phone
   numbers, outlets, airlines) comes only from the verified content layer, and every item carries
   its source and retrieval date. If we do not have a fact, the UI says so and points to the
   official channel. No invented partners, prices or capabilities.
3. **Label the kind of guidance.** Every recommendation is tagged as one of: `official`
   (instruction or fact from an authoritative source), `estimated` (our calculation or typical
   value), `suggestion` (optional idea), `demo` (simulated).

## 2. Stack

- Next.js 16.4 App Router, React 19.3, TypeScript (strict), Tailwind CSS 4.3 (`@theme` tokens in
  `src/app/globals.css`), Turbopack.
- Accessible primitives: `radix-ui` (Dialog, Popover, Tabs, Accordion, Select, Tooltip,
  ToggleGroup, VisuallyHidden). Icons: `lucide-react` only, via `src/components/ui/icon.tsx`.
- Validation: `zod`. Search: `minisearch`. No other runtime dependencies without a strong reason.
- Fonts are self-hosted with `next/font/local` (files in `src/fonts`). No third-party network
  requests at runtime: no analytics, no font CDNs, no map tiles, no embedded widgets.
- Tests: Vitest (unit, `*.test.ts` next to the code), Playwright + `@axe-core/playwright`
  (end-to-end in `e2e/`).

## 3. Rendering model

- Every page is statically prerendered. Content is imported from typed modules at build time.
- Anything that depends on the clock, the user, or storage runs in Client Components after
  hydration: demo flight boards, "open now", saved journey, theme, language, accessibility
  preferences, selected airport. Server Components never read the current time or random values.
- Client state lives in `localStorage` behind `src/lib/storage.ts` (safe wrappers, versioned keys,
  `useSyncExternalStore` hooks). Nothing personal is sent to the server.
- Route handlers under `src/app/api/*` exist to demonstrate the integration layer
  (`/api/flights`, `/api/concierge`, `/api/health`). Pages must keep working if they fail.
- The site must stay useful with JavaScript disabled for static guidance (transport, parking
  rates, facilities, guides, contacts): those are server-rendered HTML.

## 4. URL map and ownership

Every page lives under a locale segment: `src/app/[lang]/…` with `lang` = `en` or `ms`
(Bahasa Malaysia). The table below omits the `/[lang]` prefix for brevity: `/[airport]/flights`
means `src/app/[lang]/[airport]/flights/page.tsx` and the public URL `/en/kul/flights`.
`generateStaticParams` returns both locales, so every page is prerendered in both. The bare `/`
redirects to the visitor's locale (cookie, then `Accept-Language`, then `en`). API routes are not
localised (`src/app/api/*`). Build internal links with `localeHref(lang, '/kul/flights')` or the
`LocaleLink` component: never hard-code `/en`.

`[airport]` is the lowercase IATA code (`kul`, `pen`, `bki`, `kch`, `lgk`, `szb`, …). KLIA is ONE
airport (`kul`) with two terminals; terminal is a filter (`?t=T1|T2`), never a separate site tree.

## 6. Content model (summary; `src/content/types.ts` is authoritative)

- `Source { id, title, publisher, url, retrieved (ISO date), asOf? }`. Every content item has
  `sources: string[]` (ids from `sources.ts`).
- `Provenance = 'official' | 'estimated' | 'suggestion' | 'demo'`.
- `Airport { code, slug, icao?, name, shortName, city, state, classification: 'international' |
  'domestic' | 'stolport', depth: 'full' | 'essential' | 'listing', timezone, coordinates,
  terminals: Terminal[], summary, contacts, sources }`.
- `Terminal { id: 'T1' | 'T2' | 'MAIN', name, levels: Level[], airlines?: string[] }`.
- `Facility { id, airport, terminal, name, category (prayer-room | nursing-room | toilet |
  accessible-toilet | lounge | hotel | clinic | pharmacy | baggage | wifi | atm | money-changer |
  sim | information | lost-property | play-area | smoking | shower | rest | charging | water |
  porter | assistance | calm-room | viewing | other), zone: 'landside' | 'airside' | 'both' |
  'unknown', level?, locationNote?, hours?, description, accessible?, mapPoint?, sources }`.
- `Outlet { id, slug, airport, terminal, name, kind: 'dine' | 'shop' | 'service', category,
  cuisine?, zone, level?, locationNote?, hours?, priceBand?, halal?, description?, sources }`.
  Only outlets confirmed by an official source. Unknown fields stay undefined; the UI shows
  "Not published" rather than guessing.
- `TransportOption { id, airport, mode: 'rail' | 'bus' | 'taxi' | 'e-hailing' | 'car-rental' |
  'private-car' | 'shuttle' | 'inter-terminal', name, operator?, destinations: [{ name, fare?,
  duration?, note? }], frequency?, hours?, boarding: { terminal, level?, note }[], payment?,
  accessibility?, bookingUrl?, provenance, asOf?, sources }`.
- `CarPark { id, airport, terminal?, name, type, bays?, walk?, rates: RateBand[], dailyMax?,
  payment?, features: string[], accessibleBays?, evCharging?, bookingUrl?, asOf?, sources }` with
  a pure `calculateParking(carPark, minutes)` in `src/lib/parking.ts`.
- `Guide { slug, title, summary, audience[], steps/sections with provenance tags, airports?,
  sources }`, `Faq`, `Notice { id, airport?, severity, title, body, validFrom?, validTo?,
  provenance, sources }`.
- `MapModel` per terminal: schematic levels, zones, points of interest and a walk graph. Maps are
  schematic demonstration maps: every map screen says so.

## 7. Flight data

- `FlightDataProvider` interface (`listFlights`, `getFlight`, `search`) with `meta { mode: 'demo'
  | 'live', generatedAt, source, refreshSeconds }`.
- `DemoFlightProvider`: deterministic, seeded by airport + local date. It builds a plausible day
  from a route template (real airlines and real destinations for that airport, taken from the
  content layer), then derives status from the current time (scheduled, check-in open, boarding,
  gate closed, departed, delayed with new time, cancelled, landed, baggage on belt). Flight
  numbers follow the airline's real prefix but the schedule is synthetic, so every surface that
  shows a flight row shows the demo label.
- Flight id format: `<airlineCode><number>-<yyyymmdd>-<d|a>`, for example `mh2610-20261117-d`.
- An `OfficialFlightProvider` stub documents the mapping to the public MAHB flight board schema
  observed in the audit. It is not wired to any network call.

## 8. Cross-cutting behaviour

- **Airport context**: no airport is assumed. The last chosen airport and terminal are remembered
  locally and offered as a default the user can change in one tap. `useAirportContext()`.
- **Journey modes**: departing, arriving, transiting, meeting. The mode reorders quick actions and
  content blocks everywhere it appears (`useJourneyMode()`).
- **Saved journey**: flights, places and a parked-car note in local storage (`useSavedJourney()`).
  Notifications are opt-in through the browser permission prompt, and are demo notifications.
- **Language**: English and Bahasa Malaysia through the `[lang]` route segment. Interface strings
  come from typed dictionaries in `src/lib/i18n` (`getT(lang)` in Server Components, `useT()` in
  Client Components; both return `t('key', vars?)`). Never hard-code interface copy in a
  component: add a key to BOTH dictionaries. Long-form verified content (facts, guides) is
  authored in English with optional `ms` fields (`LocalizedText = { en: string; ms?: string }`,
  read with `pick(text, lang)`); when a Malay page falls back to English content it shows the
  `TranslationNotice`. `<html lang>` is set by the root layout from the route.
- **Accessibility preferences**: text size (100/112/125%), high contrast, reduced motion, theme
  (light, dark, system). Applied as `data-*` attributes on `<html>` before hydration.
- **Search**: one index over airports, facilities, outlets, transport, car parks, guides, FAQs,
  notices and corporate pages, plus live lookup of demo flights. Command palette on `/` key and
  `Ctrl/Cmd + K`; full results at `/search?q=`.
- **Concierge**: answers only from the content layer and the flight provider, cites sources, labels
  provenance, escalates to official contacts, works with no AI service (deterministic retrieval
  mode). An optional server-side Claude model can rephrase grounded answers when
  `ANTHROPIC_API_KEY` is set; it never receives personal data beyond the question and context.
- **Offline**: web app manifest and a service worker that caches the shell and static guidance.

## 9. Accessibility rules (WCAG 2.2 AA is the floor)

- Semantic landmarks, one `h1` per page, ordered headings, a skip link, visible focus
  (`:focus-visible`, never removed), focus not obscured by sticky bars (scroll-padding).
- Targets at least 24 by 24 CSS px everywhere, 44 by 44 for primary touch controls.
- No information by colour alone: statuses always have text and an icon.
- All inputs labelled; errors announced; live regions for search results counts and board updates
  (polite, never spammy). No drag-only interactions: every map action has a button alternative.
- Respect `prefers-reduced-motion` and the in-app setting. No autoplay, no carousels that move on
  their own.
- Text contrast at least 4.5:1 (3:1 for large text and UI boundaries) in both themes and in high
  contrast mode. Body text never below 16px on mobile.
- Language of parts marked (`lang="ms"`) for Malay phrases inside English pages.

## 10. Code conventions

- Server Components by default; add `'use client'` only at the leaf that needs it. Keep client
  bundles small: no content-layer imports of whole airports into client components when a prop
  will do.
- Named exports, one component per file, `kebab-case.tsx` files, `cn()` for class merging.
- Tailwind utilities with the design tokens only (no hard-coded hex colours, no arbitrary pixel
  values where a token exists). Dark theme and high contrast come from tokens, not per-component
  overrides.
- Dates and times: always in the airport's timezone via `src/lib/time.ts`; 24-hour clock; show
  the timezone when it differs from the user's.
- Every page exports `metadata` (title, description). Use `PageHeader` and `Breadcrumbs`.
- No `any`. No `eslint-disable` without a comment explaining why. No TODOs left in shipped UI.
- Copy: plain, warm, direct. Sentence case. British/Malaysian English spelling. No exclamation
  marks, no marketing filler. Say what the passenger should do.
- Tests: pure logic gets unit tests (providers, status logic, parking calculator, timeline
  builder, search, concierge retrieval). Each feature adds at least one Playwright journey test
  with an axe check.

## 11. Definition of done for a feature

1. `npm run typecheck`, `npm run lint`, `npm run test` pass; `npm run build` succeeds.
2. Works at 360, 768 and 1440 px, in light, dark and high-contrast, with keyboard only.
3. Demo data and provenance labels are present wherever required by section 1.
4. No fabricated facts: every published value traces to a source in the content layer.
5. You looked at your own screenshots (desktop and mobile) and fixed what was weak.
6. A short hand-off note is appended to `docs/engineering/handoffs/<feature>.md`: what was built,
   files, known gaps, anything a reviewer should test.
